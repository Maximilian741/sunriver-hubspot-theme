SunRiver ← App Development

Kotlin and Jetpack Compose, Material 3, and a Play Store release pipeline we own end to end. We test on the cheap, slow devices your users actually carry, not just the flagship in the office.

ScopeKotlin & Jetpack ComposeMaterial 3 by the bookPlay Store release & signingBackground work & offline syncPerformance on low-end devices

What we focus on

We write in idiomatic Kotlin and build the whole UI in Jetpack Compose, so there are no XML layouts to keep in sync with code. State is driven by coroutines and Kotlin Flow exposed from ViewModels, which keeps the main thread free and makes the data flow easy to test. The result is fewer lines than the old View system and far less boilerplate to maintain over the app’s life.
Material 3 is more than a coat of paint, we wire up dynamic color (Material You) so the palette adapts to the user’s wallpaper on Android 12 and up, with a sensible fallback theme below that. Type and spacing follow the Material 3 scale rather than hand-picked pixel values, and we build the dark theme and TalkBack content descriptions in from the first screen instead of retrofitting them. That means proper contrast, focus order, and large-text support without a separate accessibility pass at the end.
We enroll the app in Play App Signing so Google holds the upload key securely and you are never one lost keystore away from being unable to update. Releases go out as Android App Bundles (.aab) through staged rollouts, starting at a small percentage and watching crash and ANR rates in the Play Console before going wider. You keep full ownership of the Play account and release tracks; we operate the pipeline, but nothing about it is a black box you can’t see into.
Deferrable jobs, uploads, syncs, periodic refreshes, run through WorkManager, which respects Doze and battery limits and survives reboots and process death. Local data lives in a Room database (SQLite under the hood) so the app is fully usable with no signal, and we design an explicit sync strategy with conflict resolution rather than blindly overwriting. When connectivity returns, queued changes reconcile cleanly instead of silently dropping a user’s work.
We generate Baseline Profiles so the most-used code paths are ahead-of-time compiled on first launch, which measurably cuts cold-start and jank on cheaper hardware. Cold-start and frame timings are tracked against an explicit budget using Macrobenchmark, run on real low-end devices rather than a high-end emulator. That keeps the app feeling responsive on a three-year-old phone, which is what most of your users are actually holding.

Swift and SwiftUI built to the Human Interface Guidelines, shipped through TestFlight, and tuned for App Store review before we submit. Privacy and ATT handled correctly.

ScopeSwift & SwiftUIApp Store review & TestFlightHuman Interface GuidelinesPush & notificationsPrivacy & App Tracking Transparency

What we focus on

We build in Swift with SwiftUI as the primary UI layer, reaching for async/await for concurrency and Combine only where its reactive model genuinely fits. Layouts are adaptive, the same codebase scales from a compact iPhone SE up to a full iPad split view without forking the UI. Where SwiftUI has rough edges, we drop down to UIKit through representable wrappers so you never get stuck waiting on a framework gap.
Stakeholders get real builds early through TestFlight, so feedback comes from the actual app on their own devices instead of screenshots. Before we submit, we self-audit against the current App Review Guidelines, the items that trigger most rejections, like account deletion, privacy disclosures, and clear purpose strings, so the first submission is the one that gets approved. That avoids the multi-day rejection ping-pong that quietly wrecks launch dates.
We follow Apple’s Human Interface Guidelines so the app behaves the way iOS users already expect: standard navigation patterns, native gestures, and system controls rather than reinvented ones. Dynamic Type is supported so text scales with the user’s accessibility setting, and Dark Mode is a first-class path. The payoff is an app that feels Apple-made and doesn’t fight the platform.
Push goes through the Apple Push Notification service (APNs) using token-based authentication, and we implement both rich notifications with media and silent pushes for background updates. We also time the permission prompt deliberately, asking in context after the user sees the value, not on first launch, which is the single biggest lever on opt-in rates. Notification content and actions are built to be useful rather than noisy, so people leave them turned on.
Privacy nutrition labels and the app’s privacy manifest are filled in honestly to match what the code actually collects, because mismatches are a common and avoidable rejection. We only present the App Tracking Transparency (ATT) prompt when the app genuinely tracks across other companies’ apps and sites, with a clear purpose string explaining why. Data handling is designed to hold up under reviewer scrutiny, so privacy is correct by construction rather than patched after a rejection.

Cross-platform with Electron when you want one codebase, or native .NET on Windows and Swift on macOS when you need the metal. Either way it ships signed, notarized, and updating itself silently.

ScopeElectron / cross-platformNative Windows (.NET)Native macOSAuto-updateCode signing & notarization

What we focus on

When one codebase across all three platforms is the priority, we use Electron and make it feel native on each OS rather than shipping an obvious web wrapper. That means real platform menus, a working system tray, native file and save dialogs, and OS-appropriate keyboard shortcuts. We also keep the bundle disciplined, trimming the runtime and isolating the renderer with context isolation, so it stays reasonably light and secure.
When you need deep Windows integration and a small memory footprint, we build natively on .NET with WPF or the newer WinUI. That unlocks things Electron can’t do as cleanly: tight OS hooks, native performance, and per-machine resource use that IT will accept. We package it as MSIX or a traditional MSI so your IT team can deploy and update it silently through their existing tooling.
For a Mac app that must feel genuinely native, we build on AppKit or SwiftUI rather than a cross-platform shim. The app runs sandboxed to meet Apple’s requirements, ships as a universal binary that runs natively on Apple silicon and Intel, and updates through the Sparkle framework. The result behaves exactly like a Mac user expects, right down to system menus, services, and window behavior.
Updates install silently in the background, via Squirrel/electron-updater on Electron or Sparkle on macOS, so users always end up on the build you intend without hunting down an installer. We roll updates out in stages and watch for problems before going wide, with the ability to halt or roll back a bad release. That turns updating from a support headache into something nobody has to think about.
On Windows we sign with an Authenticode certificate so Microsoft SmartScreen stops warning users away from your installer, and we recommend an EV certificate when reputation needs to build fast. On macOS we sign with a Developer ID and run the app through Apple’s notarization service, then staple the ticket so Gatekeeper lets it launch cleanly offline. Done right, users never see a scary “unidentified developer” or “unrecognized app” dialog.

React and Next.js in TypeScript, talking to GraphQL or REST APIs, installable as an offline PWA, and built to WCAG 2.2 AA so everyone can use it.

ScopeReact & Next.jsTypeScript end to endGraphQL & REST APIsOffline PWAAccessibility (WCAG)

What we focus on

We build on Next.js and lean on React Server Components plus route-level code splitting so the browser only downloads the JavaScript a given page actually needs. That keeps first paint quick and the client bundle lean, with rendering chosen per route, static, server, or client, based on what the page really requires. The result loads fast on first visit instead of shipping a giant single-page bundle up front.
TypeScript runs in strict mode across the whole stack, from the API client all the way to the UI components, so the compiler catches mismatched shapes and null bugs before they reach a user. Types are shared rather than duplicated, which means a change on the data layer surfaces as a compile error anywhere it breaks the UI. That eliminates a whole category of runtime errors and makes large refactors safe.
Whether the backend speaks GraphQL or REST, we generate the client types directly from the schema (or an OpenAPI spec) so the front end and back end physically cannot drift out of sync. Caching and request de-duplication are handled by a mature data layer, typically TanStack Query or a GraphQL client, rather than ad-hoc fetch calls. When the API contract changes, the build tells you exactly what needs to update.
We add a service worker and a web app manifest so the app is installable to the home screen and keeps working when the connection drops or gets flaky. Sensible caching strategies serve the shell and key data instantly on repeat visits, with a clear plan for how stale content is revalidated. That gives users a near-native experience, fast loads and offline resilience, without shipping anything to an app store.
Accessibility is built in to WCAG 2.2 AA, not bolted on: every interaction works from the keyboard, focus order is logical, and ARIA is used only where native HTML semantics fall short. Color contrast is checked against the AA thresholds during development, and we verify the real experience with an actual screen reader before launch rather than trusting an automated scan alone. The outcome is an app that’s usable by everyone and stands up to an accessibility audit.
